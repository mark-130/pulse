# Decisions (07/11/2026 unless stated)
- D1 Single container, API plus static web. Fits the homelab pattern and Watchtower.
- D2 SQLite, single user, one volume.
- D3 Reuse the existing Garmin MCP server rather than a second Garmin client. One login, one place to fix quirks.
- D4 Superseded by D22. Races came from the Running Events Google calendar.
- D5 All writes go through the proposal engine with a confirm tap.
- D6 Own login. Tailscale identity headers rejected because LAN clients can spoof them.
- D7 Image from GHCR with the Watchtower label. Outcome (07/11/2026): the repo mark-130/pulse is private and CI pushed ghcr.io/mark-130/pulse:latest and :<sha> (run on commit d458f62). The package inherits the repo's private visibility, and Watchtower has no GHCR credentials (D13), so it cannot pull the image until Mark makes the package public or adds credentials. Package visibility is changed by Mark, not by NGtive Split (code name pulse) tooling. The Dockerfile carries org.opencontainers.image.source so the package links to the repo.
- D8 Google OAuth app in production mode to avoid 7 day token expiry.
- D9 Models configured by env, not hard-coded.
- D10 Plan app workouts read from get_scheduled_workouts. Garmin Coach tools not used.
- D11 Host port 8210 on the LAN (mapped to 8200 inside the container). Host port 8200 is taken by Duplicati. HTTPS on the tailnet at port 8443 through tailscale serve, forwarding to http://localhost:8210.
- D12 (07/11/2026, Phase 0 discovery) Internal Garmin MCP URL: http://garmin-mcp:8000/mcp (container garmin-mcp on the homelab network, streamable HTTP, no auth on the direct port). The nginx container garmin-mcp-proxy fronts it with a token and is not used by NGtive Split. A read-only initialize and tools/list succeeded: 157 tools. All 24 read tools and 3 write tools named in INTEGRATIONS.md exist, so no drift. The server also has schedule_week, schedule_workouts and unschedule_workouts: not in the allowlist, NGtive Split will not call them.
- D13 (07/11/2026) Watchtower: label-enable mode, runs daily at 04:00, notifies via ntfy. It has no Docker config.json mounted, so it holds no GHCR credentials. The ghcr.io/mark-130/pulse package must be public, or credentials added to Watchtower, or auto-update will fail.
- D14 (07/11/2026) Superseded by D21. No Homer tile.
- D15 (07/11/2026) pnpm 12 and TypeScript 6: typescript-eslint does not yet support TypeScript 7, so TypeScript is pinned to 6.x. pnpm build scripts are allowed only for better-sqlite3 and esbuild (allowBuilds).
- D16 (07/11/2026) The API is bundled with esbuild into one file. Only better-sqlite3 is installed at runtime in the image. Login rate limiting keys on the socket address, so behind tailscale serve all tailnet clients may share one address. Acceptable for a single user.
- D17 (07/11/2026) Nightly SQLite backup is in ARCHITECTURE.md but not in the Phase 0 scope. It moves to Phase 1 with the first real data.
- D18 (07/11/2026) CI runs on GitHub hosted runners (ubuntu-latest). The only self-hosted runner is registered to mark-130/homelab-config, so jobs on mark-130/pulse stayed queued. Switching back means registering a runner for this repo and setting runs-on: self-hosted.
- D19 (07/11/2026) Session cookie Secure flag follows PULSE_BASE_URL (https only), never request headers. Use an http base URL for the LAN. If a https tailnet URL is also used, the cookie is still accepted there without Secure.
- D20 (07/11/2026) Display name is NGtive Split (APP_NAME and APP_SHORT_NAME in packages/shared). The code name pulse stays. Reason: renaming infrastructure would break the GHCR image path and volumes for no visible gain. Unchanged: repo, image, container, compose service, folders, volume paths, port, env var prefixes, database file, and the "Pulse Training" calendar name (a Phase 5 Google-side name, rename if wanted).
- D21 (07/11/2026) NGtive Split gets no Homer tile, by choice. The installed PWA and bookmarks are the way in. The standing Homer convention for other apps is unchanged. deploy/homer-entry.yml is removed.
- D22 (07/11/2026) Supersedes D4. Races come from the Garmin calendar (get_calendar_events), synced by the Phase 1 Garmin job. Stored fields: title, date, start_time_local, time_zone, distance_m, goal_time_seconds, is_race, primary_event, subscribed, location, url, event_uuid. A Pulse-owned race_meta table (keyed by event_uuid, else date plus normalised title) holds priority, type, goal override and notes; edits are local and need no confirm tap. NGtive Split never writes to the Garmin calendar, so races are added in Garmin Connect. Removed: @pulse description tagging, Google to Garmin matching, the calendar.tag_race proposal kind and the Running Events calendar id. Google OAuth (D8) and Google Calendar move to Phase 5, scope to be agreed; Home Assistant moves to Phase 6. The Phase 0 placeholder race table is replaced by a migration in Phase 1. Reason: Garmin already carries the race data Mark maintains, so one source removes OAuth, matching and write-back.
- D23 (07/11/2026) The look is "Orb": teal-black background, mint accent, the orb as the presence of AI, Sora for headings and DM Sans for body. Fonts are self-hosted (@fontsource) so the PWA works offline and makes no CDN requests. The mockup lives in Mark's Claude canvas and is not readable by tooling, so docs/DESIGN.md holds the tokens and rules. Tabs become Today, Week, Ask, Races, Trends; Proposals and Settings keep their routes and are reached from the Today proposals card and the sync status sheet.
- D24 (07/11/2026, Phase 1) The Garmin sync is read only and uses an allowlist of 21 get_ tools, enforced in code and by a test that no write tool name appears in the API source. Races and workouts sync every 30 minutes with backoff, ntfy alert after 3 failures at most once a day. D17 is done: the nightly backup runs at 03:10 and keeps 7 copies. The race table was replaced by a migration (the Phase 0 table was empty).
- D25 (07/11/2026, Phase 1) Today shows Garmin's own training readiness score and level, not a go or rest verdict. The verdict needs the rules in TRAINING.md and arrives with AI in Phase 4. Races are shown as Garmin holds them, including events with is_race false. Priority, taper status and data quality flags are Phase 2.
- D26 (07/11/2026, Phase 1) Offline support: the service worker caches the read-only API responses (network first, 7 days) so the last snapshot shows without a connection. Sign out deletes that cache. Session state is cached too, so the app opens offline while a session cookie exists.
- D27 (08/11/2026, Phase 1 fix) Partial sync and retry. Found on the real phone: one Garmin Connect read timeout on the activities call (15 second upstream read timeout) made the whole app stale for 95 minutes, because the job threw on any essential failure, last_ok did not move, and the pill and banner read that one job time. Now each kind records its own outcome, a failure in one kind never blocks the others, and a run is failed only if nothing could be fetched. Timeout-type errors are retried twice (10 s, 30 s) inside the job. The pill and the full banner use the oldest of plan and readiness. Activities and trends get a quiet inline note. The raw error moves behind a Details disclosure and the Sync now button gets its own full width row. Supersedes the "essential tasks decide success" rule from D24 and the single job-level last_ok for freshness.
- D28 (08/11/2026, Phase 1 change) ntfy is optional and off while NTFY_TOKEN is unset. Reason: no token exists yet, and a rejected send must never cost a sync. The notifier is a no-op without a token, sends with a 5 second timeout, and swallows and logs failures. The status API reports alertsEnabled so the sync sheet can say failures show only in the app.
- D29 (08/11/2026, Phase 2) race_meta is built as designed. Priority and type edits are local database writes with no confirm tap, through PUT /api/races/meta. Reason: nothing outside NGtive Split changes and Garmin is never written. Each save returns the previous values so the screen can undo. No priorities are seeded in code. Defaults come from the TRAINING.md inference rules, and a race stays Unclassified until both priority and type are set.
- D30 (08/11/2026, Phase 2) Defaults the TRAINING.md table left open, all advice only and editable later: half B taper 6 days (range 5 to 7), marathon B taper 10 days (not specified), recovery 3, 6 and 12 days for 10K, half and marathon (midpoints), trail adding 1 day for a 10K and 2 otherwise, C races having no taper and no recovery window. Distance classes: under 15 km is 10K, up to 35 km half, above that marathon.
- D31 (08/11/2026, Phase 2) Warning rules as built are in TRAINING.md (Warnings as built). The long run rule (a session of 90 minutes or more in the 7 days before a non-C race) is how the fixture of a 10K six days after the 08/11 long run is flagged. A cluster counts as settled only with exactly one A that Mark set himself, so an inferred A still asks him to choose.
- D32 (08/11/2026, Phase 3) Garmin writes are off by default. PULSE_GARMIN_WRITES (on or off, default off, "${PULSE_GARMIN_WRITES:-off}" in the compose file) gates every live call. While off, the full confirm flow works and is audited, but the executor makes no MCP call and no connection, and the result is recorded as a dry run. Garmin write tools are limited to reschedule_workout and unschedule_workout. schedule_workout is not built in this phase. Write tool names appear only in proposals/executors/garmin.ts (test enforced), and the read client allowlist stays read only. Every write test uses a mocked MCP client, and no write happens in development, tests or CI.
- D33 (08/11/2026, Phase 3) Engine details. Executors are importable only from the confirm route (ESLint rule plus tests) and refuse to run for a proposal the confirm route has not registered. state_hash covers the stored workout (scheduled id, name, date, duration, completed). A second pending proposal for the same scheduled workout is refused unless it is the same change, in which case the existing one is returned. audit_log is append only, enforced by database triggers as well as by code. If live state cannot be read at confirm time, nothing is sent and the proposal stays pending. Dry runs are not probed.
- D34 (08/11/2026, Phase 3) Sync conflict probe: PENDING. Amended 08/11/2026: the probe watches for 72 hours, not two syncs, because the plan app appears to push workouts in batches and a quick Verified could be wrong. Every sync that refreshes workouts compares the actual date with the expected one, the first mismatch ends the watch as Reverted, and every check is audited. Mark runs the live steps (see the Phase 3 demo checklist), turns PULSE_GARMIN_WRITES on for the test, moves one test workout, and reports whether the plan app reverts it. The app records the outcome per proposal (Verified or Reverted by the plan app). The result goes here, and then PROBE_RESULT_RECORDED is set to true and the "plan app may revert this" note is removed. If the plan app reverts moves, reschedule proposals are reconsidered.
- D35 (08/11/2026, Phase 4a) Readiness verdict thresholds. TRAINING.md gave the inputs and the four outputs but no numbers, so the defaults are written down in TRAINING.md (Daily readiness verdict) and live as constants in verdict.ts. Points scoring: caution 1, poor 2, with the rules for Rest, Swap for recovery, Go but easier and Go as planned. With fewer than 3 of 6 measures the output is "No verdict" and says why, rather than guessing. These are starting points to tune after a few weeks of real days, and are advice only.
- D36 (08/11/2026) Phase 4 is split. 4a: AI client, usage and cap, verdict, briefing, Ask (read tools only). 4b, later: race lead-up (replaced the first idea of a taper planner, see D42), weekly review, post-run debrief, propose_* tools, ntfy for the briefing, forecast. Reason: the write-shaped tools and the planners are the riskiest part, and 4a gives Mark a safe base to run against real data first.
- D37 (08/11/2026, Phase 4a) AI guardrails as built. No key means AI is off everywhere and the rest of the app is unchanged. A hard monthly cap (default £5) checked before every model call. Briefing uses ANTHROPIC_MODEL_FAST, Ask uses ANTHROPIC_MODEL_SMART. Prices were read from the Anthropic pricing page on 08/11/2026 and dollars are converted at AI_USD_TO_GBP (default 0.78, an estimate Mark can change). Illness, pain and injury questions get a fixed reply written in code and never reach the model, so the AI cannot talk him into training through them. The AI quotes the verdict and cannot change it. Ask has six read tools and no write-shaped tool.
- D38 (08/11/2026, Phase 4a) The briefing is generated by the 06:30 job, and once on demand when Today is opened and today's is missing (the server allows one a day, one at a time, and waits 10 minutes after a failure). It is written from the data as it was at that moment and says if any data group was stale. It is not rewritten later in the day.
- D39 (08/11/2026, tooling between phases) Updating the app from the phone. Build identity: CI passes GIT_SHA and BUILD_TIME as Docker build args, which become the org.opencontainers.image.revision and created labels and the env vars PULSE_BUILD_SHA and PULSE_BUILD_TIME. GET /api/health/version serves them without a session on purpose (the browser polls it while the app restarts) and holds no secret. Update check: an anonymous read of the :latest labels from GHCR (token, manifest, linux/amd64 manifest out of the index, config blob), cached 10 minutes, and a failed check only 1 minute. It works only while the package is public (D13). Update now is a proposal of kind app.update through the same engine, audit log and import restrictions, with its own executor file (executors/app.ts, importable only from confirm.ts). The executor takes the nightly VACUUM INTO backup, then calls Watchtower GET /v1/update with image=ghcr.io/mark-130/pulse fixed in code and Authorization: Bearer from WATCHTOWER_TOKEN (env only, redacted from logs, errors, responses and stored rows). Off while WATCHTOWER_TOKEN is empty. Because Watchtower stops this container while the request is open, the proposal is saved as applied and the "called" audit entry written before the request, a dropped connection counts as expected, and the final outcome is settled by the next process (or any request after 3 minutes) from the running build: update.completed or update.not_completed. A failed check never blocks Update now: the new build is then shown as unknown. Finding at build time (08/11/2026): the Watchtower container is on the network watchtower_default only, not homelab, and has none of the HTTP API variables set, so Mark must put it on a network this app shares (or attach this app to watchtower_default) and add WATCHTOWER_HTTP_API_UPDATE, WATCHTOWER_HTTP_API_TOKEN and WATCHTOWER_HTTP_API_PERIODIC_POLLS. Without the last one, enabling the HTTP API turns the 04:00 schedule off.
- D40 (08/11/2026) Phase 3 signed off by Mark: the dry-run checks all passed (create, review, confirm as a dry run, reject, stale, expiry, audit). This covers the proposal engine, the Proposals screen and the dry-run flow only. It does not close D34: no live write has been made, the live probe result is still open, PULSE_GARMIN_WRITES stays off, and the AI proposal tools (4b, AI_PROPOSALS) stay off until that result is recorded as a decision.
- D41 (08/11/2026) Garmin sync windows tightened to the target rule: scheduled workouts last 3 days plus next 14 (was minus 14 to plus 90), activities 3 to 14 days (was 14), first backfill 180 days in 14 day windows one at a time with a pause and per-window retry (was one 180 day call), no splits or FIT tool on the allowlist (get_activity_splits removed, it was never called). Per-day kinds already ran one call at a time, inside the limit of two, so that part is unchanged. Consequence: the app only sees 14 days ahead, so reschedule proposals are limited to dates up to 14 days ahead (was 90). Reason: a moved workout beyond the window would drop out of the database and the verification probe would misread it as reverted.
- D42 (08/11/2026) Training content is not ours. Mark's coaching app owns all training content (sessions, load, paces, tapers, recovery, race preparation) and Garmin is the source of truth for what is scheduled. NGtive Split reports what is in Garmin and never suggests, designs or critiques training, and the AI must not either. Asked for training advice, the chat answers with facts from Garmin and says to take the question to his coach. Race classes (A, B, C) only drive display, clash flags and data quality flags, and the taper and recovery defaults (D30) are reference notes used only as windows for the clash flags, never to produce recommendations. Recorded in CLAUDE.md (golden rule 8), docs/TRAINING.md and the AI system prompt (docs/AI.md). Consequences made in the same change: a first attempt at a taper planner (suggested minutes per week, last long run dates, AI wording) was built on the wrong assumption and was replaced by a facts-only race lead-up (D43); the Races and Today screens no longer show taper chips, taper status lines, taper advice or recovery advice, and the seven day row no longer tints days; clash warnings now state the fact (no "consider shortening", no "controlled effort", no suggested taper dates); the AI is no longer given the app's Go or Rest status, taper or recovery text, only the readings and schedules; the briefing, review and debrief prompts forbid advice; a question asking for training advice gets a note in the user turn that points to the coach. Open question for Mark: the readiness verdict on Today (Go as planned, Go but easier, Swap for recovery, Rest, D35) is itself recommendation-shaped. It is signed off from 4a so it was left as it is and only flagged. The fixed illness, pain and injury reply (rest and see a professional) also stays, as a safety message.
- D43 (08/11/2026, Phase 4b) 4b as built. Race lead-up: plain code, read only from the cache, works with AI off and at the cap, no model call. It shows days to go and up to 4 weeks ending with the race week: workouts scheduled in Garmin, their scheduled minutes (distance is not shown because Garmin workouts carry a duration only), the longest scheduled session, rest days, and completed against scheduled so far. Weeks that have ended, or that lie beyond the 14 days the app sees (D41), are left out. Flags are factual: priority not set, start time unverified, other race inside the 21 day cluster window, a workout on race day, and the data quality flags. Weekly review: smart model, Sunday 19:00 London plus on demand, cached per week, shown on Week for weeks that have started. It reports scheduled against done, missed and moved, the readiness, sleep and HRV figures, and next week's schedule, never more than the last 28 days. Moves are found by comparing the daily schedule snapshots (and confirmed reschedules made in the app), so a move that never sat in a snapshot is not seen. Post-run debrief: fast model, one neutral description per running activity written after the sync that brings it in (runs from the last two days, at most three per sync, quiet when AI is off or at the cap), cached by activity id, rewritten only on Refresh. It uses the activity summary and the workout Garmin has scheduled that day (name and scheduled minutes, the only targets stored), no comparison with other runs, no coaching. Generated text lives in ai_text. Cap wording is "AI cap reached for this month" everywhere. AI proposal tools (propose_reschedule, propose_unschedule) change dates only, never workout content, and exist only while AI_PROPOSALS and PULSE_GARMIN_WRITES are both on (both default off). With either off the model is not offered them and a forced call creates nothing. The AI module may import only the engine's two creators (proposal-tools.ts), never an executor, the confirm route or a Garmin client, and an AI proposal is created_by ai and still needs Mark's confirm tap. Both flags stay off until the live probe result is recorded as a decision (D34). Briefing by ntfy and the forecast are deferred because ntfy is off.
- D44 (08/11/2026, fix) Weekly review failure, found from the app's own records. The usage table showed every review call succeeded and was billed, with output tokens exactly equal to the limit (600 for the review, 220 for the debrief, 400 for the briefing). Sonnet 5.5 cannot turn thinking off (only adaptive, per Anthropic's models list) and Haiku 5.5 thinks by default, so thinking used the whole output budget, leaving no text block ("The model returned no text.", shown as "could not be written"). The briefings hit their limit too, so earlier ones may have been cut short. The model identifiers were fine (both exist and are active, and the stack leaves the variables empty so the code defaults apply). Fix: low effort for the briefing, review and debrief, and output limits with room for thinking (3000, 4000, 2000, and 4096 for Ask), plus a rule that text cut off at the limit is never stored (it is a failure with the reason "Output limit reached before the text was finished"). Every failure now has a plain reason: Model not found, Timed out after 60 seconds, Rate limited, The AI service is overloaded, The API key was refused, The request was rejected, The AI service had an error, Output limit reached, Response could not be read, Cap reached, or a generic line. The reason is shown under a Details disclosure on every AI card (briefing, Ask, weekly review, debrief), with at most a short sanitised provider line (150 characters, no key, URL or request body), and is written to the audit record (action ai.failed, target the feature) and the log. A cap or AI-off state is not a failure and is not recorded. A recorded failure is shown again after a reload for an hour until a good result replaces it. AI text is shown through a small markdown component (bold, bullet lists, line breaks; no HTML, no live links, no dependency). A failed update shows its error once. The fix is confirmed by the usage evidence and by tests with a mocked client. It has not been run against the live API, because no live call is made in development.
- D45 (08/11/2026, fix) Findings from the first live weekly review. (1) The review said "30' Race Pace moved from 10/11 to 09/11". Root cause: the move list also counted applied reschedule proposals, and the only one was a dry run (Phase 3 dry-run checks, nothing was sent to Garmin), so it reported a change that never happened, in the direction of the proposal. Snapshots never showed a move (the workout is on 10/11 in both the schedule and its only snapshot). Fix: moves come only from the schedule snapshots, read as first snapshot date to current date, and a move belongs to the week of the workout's current date; next week's moved workouts are shown under next week as "moved from dd/mm to dd/mm". (2) Garmin removes a workout from its scheduled list once it is completed, so a past week showed nothing scheduled and the review said 0 minutes. The review now never states or compares against zero. Whether a recorded run was a scheduled workout is decided by name: Garmin has no link from an activity to its scheduled workout (checked on the live server, no workout or schedule field in get_activities_by_date or get_activity), so the workout name is matched inside the activity title after the location prefix ("Broxtowe - 50' Easy Run"), on the same date, one workout per run. It is reliable while the title keeps the workout name and can miss a renamed run. The wording is "5 runs were recorded and all 5 were scheduled workouts" or "3 of 5 recorded runs matched a scheduled workout". Missed sessions are only reported where a schedule snapshot shows a workout on a date now past with no matching activity. Where recording does not cover the days, the review says "Missed sessions cannot be checked for this week because schedule recording began on dd/mm" (or for the days before it began). The schedule history only exists from the first snapshot (07/11/2026) and cannot be backfilled, because Garmin no longer lists completed workouts. (3) Readings coverage: only two days existed. A one-off backfill of the last 28 days of readiness, sleep, HRV, resting heart rate and body battery now runs inside the sync, with the same rule as the activities backfill: 14 day windows, one at a time with a pause, two calls at a time for the per-day kinds (body battery is one ranged call per window), a failed window stops the run and is retried on its own without refetching stored days, days Garmin returns nothing for are remembered, summaries only, reads only. The review's "Readings used (of the last 28 days): ..." line is counted in code from the stored days and shown on the card, never written by the model. A real run of this code on a copy of the live database stored 28 days for each of the five kinds, and Garmin returned data for every day. (4) The briefing used "Good morning" at 20:21 because the model chose the greeting. The greeting is now chosen in code by London time (before 12:00 morning, until 17:00 afternoon, otherwise evening), the model is told to use it, and a wrong greeting at the start of the text is replaced. The Today greeting uses the same 17:00 rule (it was 18:00). The card is titled "Briefing".
