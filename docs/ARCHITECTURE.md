# Architecture

## Shape
One container. Hono API plus the built React app. SQLite in /data. Scheduled jobs in-process (croner). Modules register routes, jobs, AI tools and widgets.

## Data model (SQLite via Drizzle)
- garmin_snapshot: kind, date, payload JSON, fetched_at. Unique on (kind, date): one raw snapshot per kind per London day, replaced by later syncs the same day.
- activity: garmin_activity_id, name, type, start_local, date, distance_m, duration_s, avg_hr, max_hr, calories, elevation_gain_m, first_seen, last_seen (from get_activities_by_date, history kept)
- workout: garmin_scheduled_id, garmin_workout_id, date, name, sport, duration_s, completed, first_seen, last_seen
- race (from Garmin get_calendar_events, replaced on each sync by event_uuid): event_uuid, title, date, start_time_local, time_zone, distance_m, goal_time_seconds, is_race, primary_event, subscribed, location, url, first_seen, last_seen
- race_meta (built in Phase 2, D29; owned by NGtive Split, never overwritten by sync): meta_key, priority (A, B, C), type (road, trail), goal_override_s, notes, updated_at. meta_key is event_uuid when present, otherwise the date plus the normalised title (lower case, punctuation removed, spaces collapsed). Edits are local database writes with no confirm tap, because nothing outside NGtive Split changes. D59 adds forecast_place (what Mark typed), forecast_name, forecast_lat and forecast_lon: the Forecast place, saved explicitly and audited (action race.forecast_place, old and new).
- race_place (D59): race_key, source (manual, garmin or title), query, status (found, not_found or error), name, latitude, longitude, last_attempt, last_error. The resolved place for a race, so a name is looked up once. A changed Garmin location or title is noticed through query. A not found place is looked up again after 24 hours, a failed lookup after 25 minutes.
- race_forecast (D59): race_key, fetched_at, last_attempt, last_error, consecutive_failures, time_zone (from Open-Meteo, timezone=auto), hours (JSON, the 24 hours of the race date). One row per race inside the 14 day window. A failed refresh keeps hours and fetched_at.
- Weather module (D59, apps/api/src/modules/weather): logic.ts (compass points, weather codes, start time zone conversion, hour selection, the Today line), openmeteo.ts (the only code that calls Open-Meteo), data.ts (place resolution, the sync, reading the cache, the Forecast place save), module.ts (GET /api/races/weather?race=, PUT /api/races/forecast-place, the weather-sync job at :10 and :40, one sync_state row named weather with partial success recorded in detail). Read by the race detail card, the Today line (raceForecast on /api/today) and the get_race_weather AI tool. No AI is involved in the forecast.
- proposal, audit_log (see below). Proposal kinds built: garmin.reschedule, garmin.unschedule, app.update (target_system garmin or app).
- sync_state: job, last_ok, last_attempt, last_error, consecutive_failures, last_alert_at, detail
- briefing: date, text, data JSON (generatedAt, stale groups, the context sent), model, tokens
- chat_message: thread, role, content, tool_calls JSON
- kotcha_zone: zone (1 to 5), name, top_bpm, source (seed or manual), updated_at. Mark's manual copy of his Kotcha zones (D46). Kotcha owns the real ones. Covered by the nightly backup like every table.
- hr_zones_history: first_seen, profile, method, floors, max_hr, resting_hr, lactate_threshold_hr. One row per distinct set of Garmin zones, so a change date can be shown.
- vo2max_point: date, value, carried_forward, fetched_at. Daily Garmin VO2 max, upserted by the routine sync.
- race_prediction: date, seconds JSON by distance, garmin_date, fetched_at. One row per day from the first successful sync of the day (D47).
- personal_record: type_id, key, record_type, value, raw_value, date, first_seen, updated_at. Garmin's running records, with the day each value was first seen (D47).
- ai_text: kind, key, text, data JSON, model, tokens, created_at, primary key (kind, key). Cached AI text: weekly_review (week start) or debrief (activity id). Rewritten only on Refresh.
- daily_reading: kind, date, value, value2, value3 (primary key kind and date). Imported daily readings: sleep (score, hours), hrv, rhr, readiness, body_battery (charged, drained), endurance (weekly points), hill (overall, strength, endurance), lactate (heart rate, speed). Summaries only (D51).
- backfill_progress: kind, window_start, window_end, status (done or failed), rows, reason, updated_at (primary key kind and window_start). The history import upserts by kind and window start.
- ai_reservation: id, ts, feature, model, estimate_gbp. Money held for a model call in flight (D57). Deleted when the call finishes or fails. Rows older than 15 minutes are ignored and removed.
- ai_usage: ts, feature, model, input_tokens, output_tokens, cache_read_tokens, cache_write_tokens, cost_gbp (real, GBP)
- settings: key, value JSON (garmin_backfill windows, home coordinates, Phase 5 calendar allowlist)
- secret: name, ciphertext (AES-256-GCM, key from PULSE_SECRET_KEY)

## Races (Phase 2)
- Rules live in apps/api/src/modules/races/logic.ts as pure functions (inference, reference windows, flags, clash warnings), tested against the TRAINING.md fixtures with no race names in production code.
- GET /api/races returns every active race with the effective priority, type, distance and goal, data quality flags and the clash warnings. The taper and recovery windows are internal reference values for the clash flags and are not returned as advice (D42). It reads the database only.
- PUT /api/races/meta {key, priority, type} writes race_meta for one race (key is race.event_key). null clears a field and both null removes the row. The response carries the previous values so the screen can offer an undo. Session and CSRF are required. No confirm tap, because only our own database changes and Garmin is never written (D29).
- Today reads its next race from the same function, so the chips on the race card match the Races screen.

## AI (Phase 4a)
- apps/api/src/modules/ai: llm.ts (the small model interface tests mock), anthropic.ts (the SDK client), runtime.ts (callModel: gate, call, usage row), usage.ts (cap, month spend, status), pricing.ts, readings-summary.ts (the readings label and factual lines, D48), readings.ts (daily readings history), tools.ts (the six read tools and the data wrapper), briefing.ts, chat.ts (the capped tool loop), module.ts (routes and the 06:30 job).
- Routes: GET /api/ai/status, GET /api/briefing, POST /api/briefing/generate (only if today's is missing, one at a time, not again for 10 minutes after a failure), GET and POST /api/chat. The readings summary is part of GET /api/today (field readings). All need the session, and POST needs CSRF.
- 4b (D42, D43): races/leadup.ts (the race lead-up, pure, no AI), races/data.ts getLeadUp, GET /api/leadup?race=KEY (races module, reads only). ai/review.ts, ai/debrief.ts, ai/store.ts (ai_text), ai/coaching.ts (the training-advice note), ai/proposal-tools.ts. AI routes: GET and POST /api/review, GET /api/debriefs?ids=, POST /api/debrief. Jobs: briefing 06:30, weekly review Sunday 19:00 (Europe/London). After a sync that fetched anything the Garmin module calls onSynced, which writes missing debriefs for runs from the last two days (at most three, quiet when AI is off or at the cap).
- The lead-up needs no model: it counts what Garmin holds. Nothing in the API produces a suggested number, target or advice (D42).
- Proposal tools: propose_reschedule and propose_unschedule are offered to Ask only while AI_PROPOSALS and PULSE_GARMIN_WRITES are both on (both default off). With either off no proposal is created. They call proposeReschedule and proposeUnschedule in proposals/engine.ts with created_by ai, which only insert a pending proposal. proposal-tools.ts is the only AI file that imports proposal code, and no AI file imports an executor, the confirm route or a Garmin client (a test scans for this).
- Every model call passes aiGate first (key set, month spend under AI_MONTHLY_CAP_GBP) and writes an ai_usage row after. The AI module imports no executor, no confirm route and no Garmin client. Its only proposal import is the engine creators in proposal-tools.ts.

## App updates (tooling, D39)
- Build identity: CI stamps GIT_SHA and BUILD_TIME into the image (build args, the OCI revision and created labels, and env PULSE_BUILD_SHA and PULSE_BUILD_TIME). GET /api/health/version returns { sha, shortSha, builtAt } with no session needed and no secret. "dev" and null outside CI. The sync sheet and Settings show "Build cc3b793, built dd/mm/yyyy HH:mm".
- apps/api/src/modules/update: build.ts, registry.ts (anonymous GHCR read of the :latest labels), service.ts (the 10 minute cache, one check in flight), module.ts. GET /api/update gives the build, whether updating is on and the cached check. POST /api/update/check runs a check. Both read only. Results: up_to_date, available (new build and time), error (reason under Details).
- Update now: POST /api/proposals { kind: "app.update" } creates a pending app.update proposal (before is the running build, after is the newest build from the check, or null if the check failed). It is refused (409) without WATCHTOWER_TOKEN. Confirm goes through the same route as every proposal and, for this kind, checks that the running build is still the one it started from (otherwise stale), then runs executors/app.ts: audit update.requested, VACUUM INTO backup (a failed backup stops everything before Watchtower is called), audit update.backup_taken, save the proposal as applied and audit update.called and proposal.applied, then GET WATCHTOWER_URL/v1/update?image=ghcr.io/mark-130/pulse with the bearer token. The image is a constant in packages/shared, never taken from a request.
- Watchtower stops this container during the request, so the browser's confirm request normally ends in a dropped connection. Outcome: proposals/outcome.ts compares the running build with the build the update started from, at boot and on GET /api/update and GET /api/proposals. A different build is update.completed. The same build 3 minutes after the call is update.not_completed. A 401, 403, 404, 429 or an unreachable Watchtower makes the proposal failed with a plain reason.
- The browser polls /api/health/version every 3 seconds (tolerating the dropped connection) for up to 3 minutes: "Updated to cc3b793" or the timeout message with Details.
- Extra audit actions: update.requested, update.backup_taken, update.called, update.completed, update.not_completed.

## Heart rate zones and VO2 max (D46)
- apps/api/src/modules/zones: logic.ts (pure: choose the running profile or DEFAULT, the tops, differences, the warning text), data.ts (reads, the explicit Kotcha save, the confirm), module.ts. Routes: GET /api/zones, POST /api/zones/kotcha {tops} (validated: whole numbers, ascending, zone 5 equals Garmin's max), POST /api/zones/confirm, GET /api/vo2max?days=7 to 400. They read the cache. The only writes are to kotcha_zone and the confirmed-zones setting (kotcha_confirmed_garmin), each on a tap and audited. Nothing can write to Garmin or Kotcha.
- Sync: kinds hr_zones (every sync, one call, with the running then DEFAULT rule) and vo2max (one 90 day call into vo2max_point), both in the trends freshness group with per-kind success, failure and retry like the others. A new set of Garmin zones adds a hr_zones_history row.
- The warning is derived from the latest successfully stored zones against the confirmed zones, so a failed or stale fetch cannot raise or clear it.

## Fitness (D47)
- apps/api/src/modules/fitness: data.ts (getFitness: predictions with pace, record and difference, VO2 max, endurance with Garmin's band, hill, lactate threshold, running records) and module.ts (GET /api/fitness). Reads the cache only. The calculations (pace, differences, distance matching) are pure functions in packages/shared/src/fitness.ts, shared with the screen.
- Sync kinds: race_predictions (also writes race_prediction on the first sync of a day), endurance_score (reused, now with Garmin's thresholds), hill, lactate_threshold, personal_records (change detection into personal_record). All in the trends freshness group with per-kind outcome. The race lead-up reads the latest stored prediction for a race whose distance is within 2 percent of a prediction distance.
- Web: Trends has two tabs, Readings and Fitness (?tab=fitness).

## Auth
Single user. Password checked against a scrypt hash (salt:hash in hex) in PULSE_PASSWORD_HASH. Signed httpOnly SameSite=Lax session cookie (30 days). CSRF token header on every non-GET. Login rate limit: 5 attempts per 15 minutes per socket address, held in memory with expired keys swept every 100 attempts and a cap of 10,000 keys (least recently used evicted, a new key is never refused, D54). Tailscale identity headers are not trusted, because other clients can spoof them. Sessions can be revoked on the server (D56): the token carries a session epoch, kept in the settings table (key session_epoch), and is only valid while that is the current epoch. Sign out bumps the epoch, so every device is signed out and a copied cookie stops working. The cookie value is still signed and the CSRF token is unchanged. Sign out needs a session and the CSRF header like any other write.

## Proposal engine (the only write path)
Built in Phase 3 (apps/api/src/modules/proposals). Phase 3 covers Garmin only, and only moving a scheduled workout to another date or removing it from the schedule.
- Creators call createProposal() (engine.ts). In Phase 3 the only creators are the manual Move and Remove from schedule actions on Week (POST /api/proposals). AI creators arrive in Phase 4. Workout content is never edited, only dates. Creating, listing and rejecting never leave our own database.
- proposal fields: id, kind (garmin.reschedule, garmin.unschedule built; the others are reserved for later phases), target_system, payload, before, after, rationale, created_by (user or ai), state_hash, status (pending, applied, rejected, expired, stale, failed), created_at, expires_at (24 hours), decided_at, result.
- state_hash is a sha256 of the canonical JSON of the workout as stored (scheduled id, name, date, duration, completed). It is compared with the live workout at confirm time.
- Idempotency by scheduled_workout_id: the same change for the same workout returns the existing pending proposal. A different change for that workout is refused (409) until the first is decided. Confirming an applied proposal again returns it and sends nothing. Two confirms at once send one write (an in-process registry of proposals being confirmed).
- Executors live one file per system under proposals/executors/ and are importable only from proposals/confirm.ts. Enforced by an ESLint no-restricted-imports rule and by tests (an import scan and a lint run on a rogue file). An executor also refuses to run unless the confirm route has registered that proposal id as being confirmed (confirmations.ts).
- POST /api/proposals/:id/confirm needs a session and CSRF (app-wide middleware for every non-GET). It requires status pending and not expired (otherwise 409). It re-fetches the workout live from Garmin with a read tool. If Garmin cannot be read, nothing is sent and the proposal stays pending (502). If the live workout is missing or its hash differs, the proposal becomes stale, the new state is stored in result.live and shown, and nothing is sent (409). Otherwise the executor runs, an audit entry is written, and the status becomes applied or failed. Before any of that is awaited, confirm claims the pending row with one atomic update (claim_token, D63). While claimed, Reject returns 409 and expiry skips it, each outcome only applies while the claim is held, and the executor checks the claim right before the write. A blocked live read releases the claim, so the proposal is pending again. Claims left by a crash are cleared at boot.
- Writes are off by default (PULSE_GARMIN_WRITES, D32). While off, the whole flow runs and is audited, but the executor makes no MCP call and not even a connection. The proposal is applied with result.mode "dry_run".
- Verification probe (D34): the plan app pushes workouts in batches, so after a live apply every sync that refreshed scheduled workouts compares what Garmin lists with the expected result (new date, or the workout gone), for 72 hours. While the window is open the proposal is Checking and records when a sync last confirmed it. The first mismatch ends the watch at once as Reverted by the plan app. If the window closes with the expected state still in place it is Verified. Every check is an audit entry (verification.checked, then verification.verified or verification.reverted). The proposal keeps only the last 5 checks. Dry runs are not probed.
- AI tool context has no reference to executors or the confirm route. ntfy messages link to the app and never carry confirm actions.
- Idempotency (Phase 5): calendar events carry extendedProperties.private.pulseKey. Garmin operations are keyed by scheduled_workout_id.
- audit_log is append only: ts, actor, action, target, payload_hash (sha256 of the canonical payload), result. The code only inserts, and database triggers (migration 0004) abort any UPDATE or DELETE. Actions written: update.* (see App updates), proposal.created, proposal.rejected, proposal.expired, proposal.stale, proposal.confirm_blocked, proposal.applied, proposal.failed, verification.checked, verification.verified, verification.reverted.
- Allowlists: Google Calendar writes do not exist until Phase 5, which will define a writable calendar allowlist (likely the app-created "Pulse Training"). Garmin write tools are limited to reschedule_workout and unschedule_workout, named only in executors/garmin.ts. schedule_workout is not built (D32). Home Assistant limited to allowlisted entities, and the domains lock, alarm_control_panel, cover and siren cannot be proposed at all in v1.

## History import (4c, D51)
- apps/api/src/modules/history: kinds.ts (per kind fetchers and tolerant parsers), engine.ts (windows, a plain sentence for an answer in an unexpected shape with the detail only in the log (D61), retry at half size, halving a too big range and remembering the size that worked, rate limit backoff, three failed windows in a row put a kind on needs attention and the run moves on, the run order, yielding), kinds.ts also holds RANGE_LIMITS, the one table of window sizes (D60), queries.ts (status, daily series with 7 day averages, year on year, the AI monthly summary), module.ts (routes, a once a minute job, shouldYield).
- Routes: GET /api/history (status), POST /api/history/start, /pause and /resume, GET /api/history/series?days=&kinds= (daily readings with 7 day averages and the stored range), GET /api/history/yoy (this year against last year). GET /api/trends takes ?days= (28 to 1100) and returns weekly distance for that many weeks, the endurance weekly points from the history, and the first stored day per series so a chart can say "Not imported yet". Everything needs a session and the POSTs need CSRF.
- The engine runs in the background after Start. State lives in settings (history_import), so a restart resumes: the history-import job (every minute) restarts a run that was running, and ends a rate limit pause after an hour. It checks the state before every window, so Pause takes effect within one window. The import state (settings, history_import) also holds attention (kind to reason, set after three failed windows in a row in that kind, cleared by a fresh Start, kept when resuming a pause) and windowSizes (kind to the size that worked after a "range too big" answer). The final state is complete, or complete_with_issues when any day is still not covered. Only a failed login, an unreachable Garmin or the rate limit pause stop the whole run (D60). busy() is the routine sync or backup running, the minute either side of :00 and :30, and 03:05 to 03:20 London. The Garmin module exposes isRunning() on its tracked jobs for this.
- The covered range is fixed when the import is created (D70): rangeFrom and rangeTo in the history_import state, never recomputed from today. Start makes a new range (the last N days ending today) only the first time or when PULSE_HISTORY_DAYS changed. Resuming, Start again after a stop, and Start on a finished import keep it. A state from before D70 has no stored range, so it is derived once from the newest finished window and stored. Days after rangeTo belong to the routine sync. Finished windows are never fetched again, so a longer range fetches only the days outside what is done.
- An import saved before D70 has no stored range. importRange rebuilds it (D71): Complete uses the newest finished window; any other state uses the later of the London date of startedAt and the newest recorded window (done or failed); with no startedAt it uses today, so a partial import never looks complete. Only Start and the run store it. Viewing the card does not write.
- Reads Garmin only, through the same read allowlist. Two tools were added, get_sleep_summary_range and get_hrv_trend (D52). The write allowlist is unchanged.
- Backup: the history sits in the existing database, covered by the nightly VACUUM INTO backups.
- Fitness: the VO2 max sparkline, the endurance weekly points and the hill and lactate sparklines use the longer history once it exists (sparklines are averaged into at most 120 points).
- AI: one new read tool, get_history_summary (D53). The other tools keep their 28 day cap and the weekly review is unchanged.

## Sync
- Windows (D41): scheduled workouts last 3 days plus next 14, activities 3 to 14 days, first backfill 180 days in 14 day windows kept in settings (garmin_backfill), see docs/INTEGRATIONS.md.
- Each module job writes snapshots. Garmin every 30 minutes with backoff, covering workouts, metrics and the race calendar. Phase 5 adds Google incremental sync with syncToken, full resync on 410.
- UI reads the database only, never live upstream calls per page view.
- Partial success (D27): every kind is stored on its own and records its own outcome in sync_state under garmin:<task> (last_ok, last_error, consecutive_failures), alongside the raw snapshot with its own fetched_at. A failure in one kind never discards or blocks the others. A run where some kinds fail is partial: the job counts as ok and keeps a note. A run counts as failed only if nothing could be fetched (or Garmin cannot be reached). Only failed runs back off 30, 60, 120 then 240 minutes and count towards the ntfy alert.
- Retry: a timeout-type error (timed out, ETIMEDOUT, ECONNRESET) on one call is retried inside the job, twice, after 10 seconds and then 30 seconds. Other errors are not retried. After two calls in one run have used up their retries, later calls are not retried, so a dead upstream cannot stall the job.
- Freshness groups (GARMIN_GROUPS in packages/shared): plan (scheduled workouts, calendar events), readiness (stats, readiness, sleep, HRV, resting HR, body battery), activities, trends. A group is as old as its oldest kind. Stale means older than 90 minutes, or never fetched.
- The header pill and the full banner use the oldest of plan and readiness. A stale activities or trends group alone never shows the full banner. It shows a quiet inline note on the cards that use it. Cards show the sync time of the groups they use.
- A future workout that Garmin stops returning is removed. Past workouts, activities and raw snapshots are kept as history. Races Garmin stops returning are marked inactive.
- Nightly backup at 03:10 Europe/London: VACUUM INTO /data/backups/pulse-YYYYMMDD-HHmm.db, newest 7 kept.
- Offline: the service worker keeps the last good response of the read endpoints in the pulse-api cache (network first). Sign out deletes that cache. So does any 401 and any session check that says signed out (D64). The session answer is never cached. The page re-checks the session on focus, on reconnect and every 5 minutes.
- ntfy alert after 3 consecutive failures, at most once per day per job.

## Security and ops
- Network (D69): the container publishes 127.0.0.1:8210:8200 only. The one route in is tailscale serve, https://home-lab.tail83f400.ts.net:8443 forwarding to http://127.0.0.1:8210, and PULSE_BASE_URL is that https URL, so the session cookie is Secure. There is no LAN HTTP route.
- Recovery if Tailscale is down on the server: SSH to the server (LAN SSH is unaffected), check the app with curl -s http://127.0.0.1:8210/api/health (the port is on loopback, so this works there), then restart Tailscale with sudo systemctl restart tailscaled and check it with tailscale status. Re-apply the serve rule if it was lost: tailscale serve --bg --https=8443 http://127.0.0.1:8210. Use 127.0.0.1 and not localhost, because the port is published on IPv4 loopback only.
- pino logging with token redaction. Secrets only in env or the encrypted secret table.
- Nightly SQLite backup (VACUUM INTO /data/backups, keep 7). Check that existing Restic jobs cover /mnt/data/AppData/pulse.
- Dockerfile: multi-stage on node:22-alpine, non-root, healthcheck on /api/health.
- Container hardening (D58, deploy/docker-compose.yml): cap_drop ALL, security_opt no-new-privileges:true, read_only: true, and tmpfs /tmp:rw,noexec,nosuid,size=64m. The only writable path is /data (database, WAL files, backups). The network is unchanged: the homelab network, host port 8210 to 8200, and outbound access to Garmin MCP, Anthropic, ntfy and Watchtower, which cannot be filtered in Compose. The Dockerfile comment lists the runtime assumptions behind these flags.
- CI permissions (D55): the workflow grants nothing by default. The check job has contents: read only. Only the image job also has packages: write. Every action is pinned to a full commit SHA with the version in a comment, and Dependabot proposes updates weekly.
- CI: GitHub Actions on the existing self-hosted runner builds and pushes ghcr.io/mark-130/pulse:latest and :sha. Watchtower pulls updates.
